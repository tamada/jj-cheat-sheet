Jujutsu で GitHub Flow を乗りこなす

Git 互換の次世代バージョン管理システム jj のレベル別チートシート。あなたのレベルを選んでください。検索はすべてのレベルを横断します。

🌱

初学者 — まずはこれだけ

jj は「うっかり」に強いツールです。保存し忘れも、ステージし忘れも、操作ミスも存在しません。最初に3つの原則を頭に入れて、あとは基本サイクルを回すだけです。

💡 3つの大原則

これを知っていれば jj の動きはすべて説明がつきます

① 作業コピー自体がコミット

いま編集中のファイルたちは @ という「常に存在するコミット」です。ファイルを編集すると、次に jj コマンドを打った瞬間に自動でスナップショットされます。「コミットし忘れて消えた」が起きません。

② git add(ステージング)は無い

インデックスという概念がありません。変更はすべて自動的に @ に含まれます。「一部だけコミットしたい」ときは、後から jj split で分ければOK(中級編で解説)。

③ すべての操作が取り消せる

jj はすべての操作を記録しています。何をやらかしても jj undo で直前の操作を丸ごと取り消せます。壊れたら undo。これが安心の源です。

jj undo

🚀 はじめる

新しくリポジトリを作る

jj git init --colocate

--colocate を付けると .git も一緒に作られ、git コマンドや既存ツール(エディタの git 連携など)がそのまま使えます。迷ったら付けておくのがおすすめ。

GitHub からクローンする

jj git clone --colocate https://github.com/OWNER/REPO

最初の設定(名前とメール)

jj config set --user user.name "はるさん"
jj config set --user user.email "you@example.com"

🔁 毎日の基本サイクル

jj の日常はこの4コマンドの繰り返し

  1. ファイルを編集する

    エディタで普通に作業。git add は不要、変更は自動で記録されます。

  2. 状態を確認する

    jj st        # 何が変わった?(git status)
jj diff      # 差分の中身を見る

  3. 今の作業に説明を付ける

    jj describe -m "トップページの文言を修正"

    git と違い「コミットする」のではなく、すでに存在するコミット(= 作業コピー)に説明を書くイメージです。

  4. 区切りをつけて次の作業へ

    jj new

    いまのコミットを完成扱いにして、その上に新しい空の作業コピーを作ります。describe + new を一度にやるのが jj commit -m "..." です。

📋 よく使うコマンド

履歴を見る

jj log

@ が今いる場所。紫の文字(change ID)は先頭1〜2文字だけでコマンドに使えます(例: jj new qpv)。

説明を付けて区切る(2つを1コマンドで)

jj commit -m "ヘッダーを追加"

jj describe -m + jj new と同じ。git の git commit -am に一番近い感覚です。

直前の操作を取り消す

jj undo

コミットの取り消しではなく「jj の操作」の取り消し。rebase でも push の記録でも戻せます。連発すればさらに過去へ。

ファイルの変更を捨てる

jj restore path/to/file   # そのファイルだけ親の状態に戻す
jj abandon               # 今のコミットごと丸ごと捨てる

過去のコミットに戻って直す

jj edit <change-id>

そのコミットが作業コピーになり、直した内容は子孫に自動で伝わります(自動リベース)。git の checkout + rebase が一発で済む感覚。

GitHub に上げてみる(お試し)

jj git push -c @-

@- は「作業コピーの親」= 完成した直近のコミット。ブランチ名は jj が自動で付けてくれます。詳しくは中級編の GitHub Flow へ。

📖 用語ミニ辞典

change ID と commit ID

change ID(紫・kからzの文字)は「変更」の一生変わらない名前。内容を修正しても同じIDのまま。commit ID(青・16進数)は git のハッシュで、修正のたびに変わります。普段は change ID を使えばOK。

@ と @-

@ = 今の作業コピー。@- = その親。@-- でさらに親。多くのコマンドは -r で対象を指定でき、省略時は @ が対象です。

bookmark(ブックマーク)

git のブランチに相当する「コミットに貼る付箋」。ただしコミットしても自動では動きません。GitHub と連携するとき(push)に必要になります。詳しくは中級編で。

匿名ブランチ

jj ではブランチ名を付けずに歴史を分岐できます。jj new で好きな場所から作業を始めるだけ。名前は push するときに考えれば十分です。

🆘 困ったときは

迷子になったら

jj st      # 今どこで何が変わっている?
jj log     # 歴史のどこにいる?
jj undo    # やっぱりさっきのは無し!

操作の履歴を見る

jj op log

「リポジトリ全体のタイムマシン」。undo で戻りすぎたら jj redo はありませんが、jj op restore <操作ID> で任意の時点に戻れます。

先端が empty のまま枝分かれしたら

複数の作業コピー(別マシン・並行操作・undo 後など)が合流すると、空で説明なしの先端が複数残ることがあります。中身のあるコミットは失われていないので慌てなくて大丈夫。

jj edit <使いたい方のchange ID>   # そちらの先端に乗り移る
jj abandon <不要な方>             # それでも残ったら捨てる

空で説明なしの作業コピーは、離れた瞬間に自動で破棄されます(auto-abandon)。多くの場合 jj edit か jj new main するだけで枝分かれは消えます。

🌿

中級者 — Git 経験者のための jj × GitHub Flow

混乱の元はだいたい3つ:「pull がない」「push はブランチではなく bookmark を送る」「bookmark は勝手に動かない」。この3つさえ押さえれば、GitHub Flow は git より楽になります。

⚡ まず混乱を解消する3枚

😵 git pull は無い 最重要

jj では「取ってくる」と「取り込む」が分かれています。

jj git fetch              # ① リモートの最新を取得
jj rebase -b @ -o main    # ② 自分の作業を main の先端に載せ替え

fetch しても作業コピーは1ミリも動きません。git pull のように「いきなりマージが始まって混乱」することがなく、②をやるかどうかは自分で決められます。

😵 push は「bookmark」を送る

git の push は「今いるブランチ」を送りますが、jj に「今いるブランチ」はありません。どの bookmark(または change)を送るか明示します。

jj git push -c @-              # この変更を送る(名前は自動生成)
jj git push -b feat-login      # この bookmark を送る
jj git push                    # 動かした tracked bookmark を全部送る

😵 bookmark は勝手に進まない

git ではコミットするとブランチが進みますが、jj の bookmark は貼った場所に留まります。push の前に手で進めるのが作法です。

jj bookmark move feat-login --to @-

毎回やるのが面倒なら熟練者編の jj tug エイリアスをどうぞ。

🔀 GitHub Flow 完全ガイド

ブランチを切る → 作業 → PR → レビュー対応 → マージ後の掃除まで

  1. 準備(最初の1回だけ)

    jj git clone --colocate git@github.com:OWNER/REPO.git
cd REPO

    clone すると既定ブランチ(main)は自動で track されます。既存の git リポジトリで始めるなら、リポジトリ内で jj git init --colocate。

  2. ブランチを切る = jj new main

    jj git fetch                  # まず最新化
jj new main -m "feat: ログイン画面"

    ブランチ名はまだ要りません。「main から新しいコミットを生やす」だけで、それが git でいう feature ブランチの開始です。名前(bookmark)は push 直前に付ければOK。

  3. 作業してコミットを積む

    # 編集 → 区切りごとに
jj commit -m "feat: フォームの見た目を実装"
# さらに編集 →
jj commit -m "feat: バリデーションを追加"

    「さっきのコミットに入れ忘れた!」は jj squash(今の変更を親に合流)。git commit --amend と違って push 済みでも安全に扱えます(後述)。

  4. push して PR を作る

    # 案A: 名前も jj にまかせる(push-xxxx という bookmark が自動生成)
jj git push -c @-

# 案B: ちゃんと名前を付ける
jj git push --named feat-login=@-

    --named は「bookmark 作成 + push」の一発コマンド。あとは GitHub 上か gh pr create で PR を作成(colocate していれば gh CLI もそのまま動きます)。

    @- ってなんで「親」を push するの?
    jj commit の後、あなたは新しい空の作業コピー(@)の上にいます。完成した仕事はその親(@-)。だから push するのは @- です。空でない @ にいるなら -c @ でも構いません。

  5. レビュー対応(コミットを積む派)

    jj new feat-login                     # bookmark の先端から再開
# 指摘を修正 →
jj commit -m "fix: レビュー指摘対応"
jj bookmark move feat-login --to @-   # bookmark を進めるのを忘れずに!
jj git push

  6. レビュー対応(履歴をきれいに保つ派)

    jj new feat-login            # 修正用の作業場を作る
# 指摘を修正 →
jj squash                     # 修正を直前のコミットに溶かし込む
jj git push                   # 自動で安全な force push になる

    直したいコミットが先端でなければ jj squash --into <change-id>。jj の force push は常に --force-with-lease 相当なので、他人の push を踏み潰しません。

  7. 作業中に main が進んだら

    jj git fetch
jj rebase -b @ -o main        # ブランチごと main の先端へ
jj git push                   # PR も更新(自動 force-with-lease)

    コンフリクトしても止まりません(下の「コンフリクト」カード参照)。-b @ は「@ を含むブランチ一式」の意味で、省略しても同じです。

  8. マージされたら掃除

    jj git fetch                  # マージ済み bookmark は自動で消える
jj new main                   # 次の作業へ!

    GitHub 側でブランチが削除されていれば、fetch でローカルの bookmark も消え、変更は main に取り込まれ済み。git のような「マージ済みブランチの削除作業」はほぼ不要です。

🔖 bookmark 操作 早見表

作る・追跡する

jj bookmark create feat -r @-   # @- に bookmark を貼る
jj bookmark track feat@origin   # リモートの bookmark を追跡
jj bookmark list                # 一覧(-a で リモート込み)

動かす・消す

jj bookmark move feat --to @-   # 付け替え(前進)
jj bookmark delete feat         # 削除(push すればリモートも消える)
jj bookmark forget feat         # jj の管理から外すだけ(リモートに影響なし)

他人の PR ブランチを見る

jj git fetch
jj new their-branch@origin     # その先端から作業コピーを作る

track していないリモート bookmark は name@remote の形で指定します。

💥 コンフリクトは怖くない

jj のコンフリクトは「状態」

git はコンフリクトで作業が中断しますが(MERGING地獄)、jj はコンフリクトをコミットの中に記録して続行します。rebase は必ず成功し、解消はいつでも好きなときに。

jj log    # × 印がコンフリクトを含むコミット
jj st     # どのファイルが競合しているか

解消のしかた

jj new <競合コミット>   # または jj edit
# ファイル内のマーカーを直す(またはマージツール起動 ↓)
jj resolve
jj squash                # new した場合は解消結果を親へ

解消すると子孫のコンフリクトも自動で解消されます。rebase のたびに同じ競合を直す git の苦行はありません。

「rebase --abort」したい

jj undo

中断という概念自体が不要。気に入らなければ操作ごと取り消すだけです。

🧰 履歴の編集(中級編)

変更を親に溶かし込む

jj squash                 # @ の内容を全部親へ
jj squash -i              # 対話的に一部だけ
jj squash --into <rev>    # 親以外の任意のコミットへ

コミットを分割する(git add -p の代わり)

jj split                  # 対話UIで「前半」に入れる変更を選ぶ
jj split path/to/file     # このファイルだけ前半に

「全部入りで作業 → 後から分ける」が jj 流。ステージングの代替です。

コミットメッセージだけ直す

jj describe -r <rev> -m "新しいメッセージ"

過去のどのコミットでもOK。子孫は自動でリベースされます。

🌳

Git 熟練者 — jj を武器にする

rebase -i / reflog / rerere でやっていたことは、jj では一級市民です。revset で歴史を問い合わせ、自動リベースを味方に付け、スタック PR を量産しましょう。

🎯 revset — 歴史へのクエリ言語

-r を取るすべてのコマンドで使える

基本記法

@           # 作業コピー
@-          # その親(@-- で祖父母)
x::y        # x から y までの経路(x:: で子孫全部, ::y で祖先全部)
x..y        # y の祖先から x の祖先を除いたもの(git の x..y)
x | y  x & y  ~x   # 和・積・否定

よく使う関数

trunk()             # main/master(自動判定)
mine()              # 自分が author
bookmarks()         # ローカル bookmark が付いた rev
remote_bookmarks()  # リモート bookmark が付いた rev
conflicts()         # コンフリクトを含む rev
heads(x)            # x のうち先端のみ
description("fix")  # メッセージで検索

実用レシピ

# push していない自分の仕事を一望
jj log -r 'mine() & ~::remote_bookmarks()'

# main に入っていない全ブランチ
jj log -r 'bookmarks() & ~::trunk()'

# 今の作業の「ブランチ全体」
jj log -r 'trunk()..@'

🔪 履歴の外科手術

すべて自動リベース付き・すべて undo 可能

jj absorb — 修正の自動振り分け 神機能

# スタック上の複数コミットに跨がる修正をしたら…
jj absorb    # 各行の変更を「その行を最後に触ったコミット」へ自動 squash

git の absorb + rebase --autosquash が組み込みで、かつ止まりません。レビュー指摘対応が一撃で終わります。

rebase の全形態

jj rebase -r X -o Y    # X だけを Y の上へ(子は繋ぎ直し)
jj rebase -s X -o Y    # X とその子孫ごと
jj rebase -b X -o Y    # X を含むブランチ一式
jj rebase -r X -A Y    # Y の「後」に挿入(-B で「前」)

-o/--onto は旧 -d/--destination。挿入系(-A/-B)は git rebase -i の並べ替えの代替です。

分割・並列化

jj split -r X             # X を対話的に2つへ
jj split -r X --parallel  # 直列ではなく兄弟に分割
jj parallelize X Y Z      # 直列のコミット群を兄弟化(独立PRへ)

過去コミットの内容を直接編集

jj diffedit -r X    # X の diff 自体を対話編集
jj edit X           # X を作業コピーにして普通に編集

コミット自身の変遷を追う

jj evolog -r X    # X が squash や rebase でどう変わってきたか

change ID は不変なので「このコミット、昨日はどんな中身だった?」に答えられます。git には無い概念です。

op log — リポジトリのタイムマシン

jj op log             # 全操作の履歴
jj op diff --op X     # その操作で何が変わったか
jj op restore X       # リポジトリ全体をその時点へ
jj undo               # = 直前1操作の op restore

📚 スタック PR(Stacked PRs)

依存し合う PR を積み上げて出す

jj では「スタックの各段に bookmark を貼る」だけ。下の段を直せば上の段は自動で追従し、push も一括です。

# base → part1 → part2 と積む
jj new main -m "refactor: 下準備"   ; # …作業… jj commit
jj new -m "feat: 本体"              ; # …作業… jj commit

# 各段に bookmark を貼って一括 push
jj git push --named refactor-base=@-- --named feat-main=@-

# GitHub で PR を2本作成(feat-main の base を refactor-base に)

# 下の段にレビューが入ったら:
jj new refactor-base ; # …修正… ; jj squash
jj git push    # 上の段も自動リベース済みで一緒に更新される

下の PR がマージされたら jj git fetch → jj rebase -b @ -o main → jj git push で上の PR を main 直付けに。

🕸 メガマージ & 高度な芸当

メガマージ — 全ブランチを同時に試す

jj new feat-a feat-b feat-c   # 3本を束ねた作業コピー
# 全部入りでビルド・動作確認。修正したら:
jj squash --into feat-a       # 該当ブランチへ送り返す

「レビュー待ちブランチを全部載せた環境で開発」という jj 名物ワークフロー。各ブランチは独立したまま PR に出せます。

複数ワークスペース(git worktree)

jj workspace add ../repo-hotfix
jj workspace list

op log と歴史は共有、作業コピー(@)だけ別。緊急対応に。

divergent change の解消

同じ change ID が2つの実体を持つと ?? 付きで表示されます(undo 後の再編集などで発生)。

jj abandon <commit-id>     # 要らない側を捨てる(commit ID で指定)
# または両方残す: jj duplicate で別 change に

git との併用(colocated)

git log --oneline    # git コマンドはそのまま動く
jj git import        # git 側での変更を jj へ(通常は自動)
jj git export        # jj 側の状態を git refs へ(通常は自動)

git HEAD は常に detached。IDE の「現在のブランチ表示」が空でも正常です。

⚙️ 設定レシピ(~/.config/jj/config.toml)

定番エイリアス jj tug 必携

[aliases]
tug = ["bookmark", "move", "--from", "closest_bookmark(@)", "--to", "@-"]

[revset-aliases]
"closest_bookmark(to)" = "heads(::to & bookmarks())"

「直近の bookmark を @- まで引っ張り上げる」。commit → jj tug → jj git push が黄金リズムになります。

保護範囲のカスタマイズ

[revset-aliases]
"immutable_heads()" = "builtin_immutable_heads() | remote_bookmarks()"

既定では trunk と タグ等が書き換え禁止(immutable)。push 済みコミット全体を保護したい場合の例です。

fork 運用(upstream + origin)

[git]
fetch = ["upstream", "origin"]
push = "origin"

upstream から取り込み、自分の fork に push。jj git clone --remote upstream URL と組み合わせて。

その他の定番設定

[ui]
default-command = "log"       # jj 単体で log 表示
diff-editor = ":builtin"      # split/squash -i の対話UI

[ui.pager]
command = ["delta"]           # diff を delta で表示

[templates]
draft_commit_description = 'concat(description, "\n", diff.stat(72))'

jj fix — 全コミット自動整形

[fix.tools.prettier]
command = ["npx", "prettier", "--stdin-filepath", "$path"]
patterns = ["glob:'**/*.ts'"]
jj fix    # mutable な全コミットにフォーマッタを適用(子孫は自動リベース)

WIP コミットの push 事故防止

[git]
